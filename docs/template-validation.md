# 템플릿 검증

템플릿 생성·버전 저장·게시에서는 `resources.yaml`과 `ui-spec.yaml`을 함께 검사한다.

- YAML 구문, apiVersion·kind·metadata.name, 이름 형식과 중복 리소스
- 폼 필드의 타입·라벨·경로 문법·정규식
- 경로가 가리키는 리소스 존재 여부와 배열 범위·중간 구조
- 이름 필드의 기본값과 다중 인스턴스 제약

게시할 때도 다시 검사하므로 과거 코드로 저장한 잘못된 초안은 수정 후 게시해야 한다.
이미 게시한 버전을 자동 변경하지 않는다. 새 버전을 만들어 수정·게시한다.

UI 모드의 리소스 이름은 폼 경로를 연결하는 기준이다. 사용자에게 노출한 이름의
기본값은 원본 이름을 덮어쓰지 않고 배포 렌더링 시 적용한다. 렌더링은 모든 필드의
대상을 먼저 연결한 뒤 값을 적용하므로 이름 필드의 순서에 따라 다른 필드가 실패하지 않는다.

## Kubernetes 검증과의 구분

위 검사는 로컬 구조 검사이며 Kubernetes 전체 스키마·admission 검증은 아니다.
예를 들어 Deployment의 selector·pod template 필수 항목이나 클러스터의 정책은
여기서 완전히 검사하지 않는다. 저장 성공이 배포 성공을 보장하지 않는다.

클러스터 검증에는 대상 클러스터·네임스페이스·사용자 권한과 실제 입력값이 필요하다.
필수 입력이 아직 없는 원본 템플릿 대신 입력값을 적용한 최종 YAML을 검사해야 한다.
새 템플릿 및 버전 편집 화면(UI·YAML 모드)의 **클러스터 유효성 검사**에서 진행한다.

1. **검증 준비 (dry-run)**를 누른다. 저장되지 않은 현재 편집 내용을 사용한다.
2. 검증 클러스터·네임스페이스·테스트 배포 이름을 지정한다.
3. 필요한 테스트 입력값을 채우고 **클러스터에서 검증**을 누른다.

API는 `POST /v1/templates/validate`다. 일반 관리자·팀 편집자만 이용할 수 있고 데모 계정은 제외한다.
호출자의 Kubernetes 토큰으로 `create` 요청에 `dryRun=All`, `fieldValidation=Strict`를 지정한다.
템플릿·릴리스·Kubernetes 리소스를 저장하지 않으며, 서버가 반환한 리소스 본문도 반환하지 않는다.
20초 제한과 호출 빈도 제한을 적용한다. 최대 50개 MVP 리소스를 검사한다.

같은 이름이 이미 있으면 충돌로 실패한다. 기존 오브젝트와 합치는 업데이트 검증은 하지 않는다.
일괄 검증 중에도 앞선 리소스가 생성되지 않으므로, 같은 템플릿 안의 아직 없는 다른 리소스를
요구하는 admission 정책에서는 거부될 수 있다. 필드·대상·편집 내용이 바뀌면 이전 결과를 지운다.
성공은 현재 입력·대상에서의 신규 생성 검증이며, 실제 배포·컨트롤러 실행 성공을 보장하지 않는다.

CLI로 배포 미리보기의 YAML을 `rendered.yaml`로 저장했다면 다음처럼 명시적인 대상에 검사한다.

```sh
kubectl --context <검증용-context> --namespace <검증용-namespace> create \
  --dry-run=server --validate=strict -f rendered.yaml
```

이 명령은 리소스를 저장하지 않는다. 원본 `resources.yaml`만 검사하면 사용자 입력이나
다중 인스턴스 이름 변환 결과는 검증되지 않는다. 일반 YAML 미리보기는 렌더링만 수행하고,
클러스터 검증 버튼을 눌렀을 때만 실제 클러스터에 dry-run 요청을 보낸다.
